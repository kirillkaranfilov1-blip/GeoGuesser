# Правила работы IDE Antigravity

## 1. Общие принципы

1. Работай только в рамках поставленной задачи.
2. Не добавляй функционал, который не был запрошен, без необходимости.
3. Перед изменением проекта изучи существующую структуру, файлы и используемые технологии.
4. Сохраняй существующую архитектуру проекта, если задача не требует её изменения.
5. Не ломай уже работающий функционал при добавлении новых возможностей.
6. Все изменения должны быть понятными, логичными и поддерживаемыми.

## 2. Правила ответов

1. Отвечай кратко и по существу.
2. Не добавляй лишнюю информацию, которая не относится к задаче.
3. Используй только проверенную информацию.
4. Не выдумывай API, библиотеки, функции, настройки или возможности.
5. Если информация не проверена или есть сомнения, прямо укажи это.
6. Если задача технически невыполнима в текущих условиях, обязательно сообщи об этом.
7. Не утверждай, что задача выполнена, если она фактически не выполнена.
8. После выполнения изменений кратко указывай, что именно было изменено.

## 3. Работа с кодом

1. Перед редактированием проверь текущий код и зависимости между файлами.
2. Не переписывай весь файл без необходимости.
3. Изменяй только те части кода, которые относятся к задаче.
4. Не удаляй рабочий код без причины.
5. Не создавай дублирующий код, если существующую логику можно переиспользовать.
6. Используй понятные названия переменных, функций, классов и компонентов.
7. Соблюдай единый стиль написания кода во всём проекте.
8. Комментарии должны добавляться в код там, где они помогают понять сложную или неочевидную логику.
9. Не добавляй комментарии ради очевидных действий.
10. Комментарии должны соответствовать фактическому поведению кода.

## 4. Чистота проекта

1. Поддерживай аккуратную структуру проекта.
2. Не создавай временные, тестовые и ненужные файлы без необходимости.
3. После выполнения задачи удаляй созданные временные файлы, если они больше не нужны.
4. Не оставляй неиспользуемые переменные, функции, импорты и зависимости.
5. Не дублируй стили, скрипты или компоненты без причины.
6. Не изменяй названия существующих файлов или папок без необходимости.
7. Новые файлы размещай в подходящих директориях.
8. Следи за тем, чтобы структура проекта оставалась понятной и предсказуемой.

## 5. Зависимости и библиотеки

1. Не добавляй новую библиотеку, если задачу можно нормально выполнить существующими средствами.
2. Перед использованием новой библиотеки проверь, действительно ли она необходима.
3. Не заменяй существующие зависимости без причины.
4. Не используй устаревшие или неподтверждённые методы.
5. Версии зависимостей не изменяй без необходимости.

## 6. Безопасность изменений

1. Не удаляй важные файлы без явной необходимости.
2. Не изменяй конфигурацию проекта без причины.
3. Не изменяй секреты, токены, пароли и ключи доступа.
4. Не помещай секретные данные непосредственно в исходный код.
5. Не выполняй потенциально опасные команды без понимания их последствий.

## 7. Проверка результата

После каждого значимого изменения:

1. Проверь синтаксис изменённого кода.
2. Проверь, что импорты и зависимости корректны.
3. Проверь отсутствие очевидных ошибок.
4. Проверь, что новая функция работает вместе с существующим функционалом.
5. Проверь консоль на ошибки, если проект это позволяет.
6. Не сообщай об успешном выполнении до проведения проверки.

## 8. Работа с существующим проектом

Перед внесением изменений:

1. Определи используемый стек.
2. Изучи структуру проекта.
3. Найди связанные с задачей файлы.
4. Изучи существующую реализацию похожего функционала.
5. Используй существующие решения вместо создания параллельной архитектуры.

## 9. Работа с дизайном и UI

1. Сохраняй существующую визуальную систему проекта.
2. Не изменяй дизайн других компонентов без необходимости.
3. Следи за адаптивностью интерфейса.
4. Сохраняй единообразие отступов, размеров, шрифтов и компонентов.
5. Анимации должны быть плавными и не мешать пользователю.
6. Не добавляй визуальные эффекты без функциональной или UX-причины.

## 10. Работа с ошибками

Если обнаружена ошибка:

1. Определи причину ошибки перед внесением исправлений.
2. Исправляй причину, а не только её визуальное проявление.
3. Не скрывай ошибки искусственно.
4. Не удаляй проблемный функционал только для того, чтобы убрать ошибку.
5. После исправления повторно проверь связанный функционал.

## 11. Ограничения агента

1. Не притворяйся, что имеешь доступ к инструменту, файлу, API или системе, которой у тебя нет.
2. Не утверждай, что что-либо протестировано, если проверка не выполнялась.
3. Не утверждай, что файл создан или изменён, если этого фактически не произошло.
4. Если выполнение задачи невозможно, прямо сообщи причину.
5. Если для выполнения задачи не хватает данных, используй доступные данные и явно укажи ограничение.

## 12. Формат выполнения задач

При выполнении задачи придерживайся следующего порядка:

1. Проанализировать существующий проект.
2. Определить необходимые изменения.
3. Внести минимальные необходимые изменения.
4. Проверить результат.
5. Удалить ненужные временные изменения.
6. Кратко сообщить результат.

## 13. Главный принцип

Код должен быть:

* чистым;
* понятным;
* проверенным;
* поддерживаемым;
* безопасным для существующего проекта;
* без лишнего функционала.

Главное правило: лучше честно сообщить, что задача не выполнена или требует дополнительных данных, чем выдать непроверенный или выдуманный результат.
